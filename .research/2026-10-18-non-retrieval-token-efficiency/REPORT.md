# 代码检索之外的 Coding Agent Token 效率研究（2026-10-18）

开发者研究与实验设计，供人工阅读；不属于 Skill 的自动加载内容。本轮没有安装工具、修改全局配置或 Skill、执行正式对照实验，也没有提交、推送或创建分支。下文不提供本项目尚未测得的节省比例。

后续讨论已明确实际宿主为 ZCode 与 Codex，同时使用订阅额度和 API。用户要求跳出输入压缩、日志过滤和现有原生能力的重复推荐。后续候选与实验门槛见 [突破输入压缩的补充研究](BEYOND-COMPRESSION.md)；本文最初的优先级不再代表后续建议。

**建议先验证两个方向，第三个方向按宿主条件决定。**

| 优先级 | 方向 | 预期减少的实际消耗 | 适用边界 |
| --- | --- | --- | --- |
| 1 | 完整证据留在本地，确定性处理后按需返回 | 大量中间工具结果首次进入上下文的 input，以及这些结果在后续请求中再次计入的 input；可编程编排还可能减少模型往返 | 日志、测试报告、构建输出、大 JSON、多结果聚合；正常输出已经很小时不强加包装 |
| 2 | 带失效检查的任务记录，复用仍有效的证据与验证 | 反复探索、重复读取、阶段交接和不必要重跑造成的 input/output 与模型轮次；长任务在必要边界配合宿主 compaction | 跨阶段、恢复会话、必要交接和反复修正；单次小改动直接完成，外部状态相关验证不能仅凭源码哈希复用 |
| 条件候选 | 宿主原生的工具 schema 按需发现 | 未用工具定义反复计入的 input | 只有实际 eager loading 且工具目录足够大才值得测；已有延迟加载时不再默认叠加网关 |

先使用现有 shell、标准库脚本、CLI 的机器报告和宿主已有执行器。RTK、Context Mode、MCP Slim 是替代实现的候选，不是这两个方向的前置依赖。

- 阅读了当前 `SKILL.md`、可选能力参考中的相关内容，以及用户指定的两份 `REPORT.md`。没有加载全部实验日志、私有源码快照或整个仓库。
- 两份旧报告和 `.research/CLEANUP.md` 在本轮开始时已有未提交状态；本轮只新增本报告。
- 两个只读研究子 Agent 均为 `gpt-6-luna / max`、独立上下文，分别研究输出处理和宿主/会话机制；主线核对关键官方页面、源码和 issue 后采用结论。没有让子 Agent 重读旧实验包或真实项目。
- 本轮只读核验了真实项目的规则、构建/验证配置和测试文件名。没有运行构建、测试、应用、索引重建或模型基准；配置声明的版本不冒充已运行程序的版本。

**已有实验能支持什么。**

[最初报告](../2026-10-18-retrieval-token-benchmark/REPORT.md)观察到重复表示、模型轮次和全局工具目录暴露等混杂因素；[后续报告](../2026-10-18-serena-incremental-benefit/REPORT.md)修正了返回处理，但 Serena 可用组没有调用 Serena。后者也没有隔离测出重复表示修复的 Token 收益。因此，不能把这些历史数字作为下面任何方向的效果估计。

它们提示应测完整工作流：一次多余返回会进入后续上下文，一次多余模型请求会再次携带当时的上下文。缓存命中可能改善价格与延迟，但这些缓存 input 仍必须计入整个任务的 Token。减少请求次数与减少中间结果，两者都值得考察。

本报告将证据分为：官方机制说明、上游源码、作者或用户案例、本轮本地观察，以及尚待实验的推断。官方或项目方展示的节省百分比均未作为本项目预期。

**方向 1：完整证据留在本地，再做确定性处理。**

最小实现是现有命令加本地脚本，而不是新增 MCP：让程序处理筛选、精确去重、计数、排序、关联和分页，让模型处理语义、异常原因与实现决策。工具结果进入模型上下文之前处理才有直接意义；先完整打印给模型，再让模型写摘要，已经支付了原始输入和摘要生成的开销。

建议的返回契约包含：原命令与工作目录、源码状态标识、退出码/信号/超时、实际执行范围、报告生成时间、测试或记录总数、失败/错误/跳过数、所有失败对象、必要诊断、解析是否完整，以及原始文件路径、哈希和可展开的位置。脚本失败、报告缺失、零测试或未知输出类型必须显式暴露。

| 对象 | 优先采用的原生组织方式 | 保留和恢复完整证据的方法 | 不适用或需要展开的情况 |
| --- | --- | --- | --- |
| 构建、测试与长命令 | stdout/stderr 完整落盘；读取 Surefire/JUnit/JSON 等报告，先返回范围、状态、计数和失败诊断 | 保存原始流及结构化报告，按测试 ID、错误块、行段取回；必要时完整读取 | 编译/收集阶段失败可能没有测试报告；测试崩溃、未处理异常、警告或成功日志本身是任务证据时，必须展开 |
| 大 JSON、API 或工具结果 | 按已知 schema 用标准库或 `jq` 验证、筛选、关联和聚合；返回输入数量、过滤条件与结果来源 | 原始响应快照含分页游标、错误和元数据；可按对象 ID 或页取回 | 开放式分析、schema 未知、需要模型判断哪些字段相关时，不能预先任意删字段 |
| Git diff | 先看状态、路径、变更量，再按文件读取完整相关 diff；机械变更可以由脚本列出精确变化 | 保留固定基线与最终文件状态，记录 staged/unstaged/untracked、重命名和二进制；未追踪文件单独读取 | `git diff --stat` 不覆盖未追踪文件；只看 diff 摘要无法完成实现或审查；不能默认忽略可能影响语义的空白 |
| 多个已知结果 | 现有执行器内完成独立只读调用、明确的依赖顺序、精确去重与聚合，最后返回一个带来源的结果 | 每个子调用的原始结果、错误、时间和分页状态可独立展开 | 每一步都需要新语义判断、权限确认、写入或副作用时，保持明确的模型/审批边界 |
| 长命令等待 | 使用现有 session ID 和完成事件，合理等待后读取新输出 | 保存同一命令的完整日志，不重复启动命令 | 频繁空轮询没有信息价值；也不能为了减少轮次让任务失去超时、失败检测或必要进度反馈 |

若做错误分组，必须保留所有失败 ID、每组数量和原始块位置；只能按可证明的规则去重，不能把“看起来相似”的不同根因折成一个。发生解析错误或输出格式升级时，回退到原始证据。分页必须真正完成，或明确报告未处理范围，不能将“只展示前 N 个”解释成完整集合。

OpenAI 的 [Programmatic Tool Calling 文档](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)明确描述了把中间结果留在执行器、用代码处理后返回的机制，也建议对语义决策和必要原生证据保留直接调用。本会话已暴露 `functions.exec` 和嵌套工具编排；这是当前会话的可观察能力，不能外推为每个 Codex CLI/Desktop 版本都具备相同实现。无此能力的宿主仍可通过 shell/Python 等完成本地处理。

本方向减少的是进入模型的中间数据和往返，不要求缩短最终交付。最终回答仍需满足同一事实、证据、异常处理和验证要求。若最后仍必须通读整个原文，分层的额外发现步骤可能更贵。

维护成本是少量命令模板、报告解析与版本适配、日志磁盘空间和清理。一次性脚本的生成、调试和修复也要计入任务；只有已经冻结并可复用的通用处理器，其一次性准备成本才可单列，仍需报告摊销。

**原生能力已经覆盖了相当一部分。**

真实项目的后端是 Java 17 / Maven 多模块，父 POM 声明 Surefire 3.2.5，并已有 Java 测试。前端配置采用 Vitest，`package.json` 声明 `vitest ^5.0.2`，已有逻辑测试；Worker 也有已有测试文件。本轮没有确认所有依赖安装完成、测试可运行或当前测试全绿。

当前 [Vitest reporter 文档](https://vitest.dev/guide/reporters)提供 JSON/JUnit 和 `minimal`（别名 `agent`），并说明 agent 检测可自动选择后者。[上游 minimal 源码](https://raw.githubusercontent.com/vitest-dev/vitest/main/packages/vitest/src/node/reporters/minimal.ts)可见对成功日志与模块/用例输出的筛选。这说明先检查现有默认行为比安装新压缩器合理。

需要区别“原始数据仍在本地”和“上游根本没有输出”：minimal 会抑制成功测试 console 日志，之后重定向 stdout 无法把这些日志恢复。需要它们时，应从首次运行就把适当 reporter 的完整输出留在本地；若只能重跑，成本也要计入。文档关于 summary 的概括与继承的 reporter 行为不宜直接等同，正式实验以安装版本的实际输出、未处理错误和退出码为准。

[Vitest issue #10217](https://github.com/vitest-dev/vitest/issues/10217)记录了显式 reporter 配置与 agent 检测的交互；[issue #10619](https://github.com/vitest-dev/vitest/issues/10619)及其实现关联记录了 v5 机器报告默认路径的变化，并给出把报告作为 CI artifact 或用 `jq` 后处理的使用实例。这些是机制和使用场景证据，不是本项目模型 usage 实测。实验必须显式确认报告路径，不能把缺少 stdout 当作测试成功。

**为什么不先安装 RTK、Context Mode。**

| 候选 | 能解决的问题与证据 | 信息、恢复和运行成本 | 当前结论 |
| --- | --- | --- | --- |
| RTK 的 OSS 命令过滤 | 项目文档描述在模型读到输出前过滤 shell 结果；可替代一些重复命令适配 | 过滤不是天然无损。[用户 issue #4098](https://github.com/rtk-ai/rtk/issues/4098)报告 rtk 0.49.0 某条 200 条截断路径没有 recall 记录，需重跑才能恢复；这是特定版本/路径的用户报告，不是所有命令都失败的证明。还需维护命令覆盖、hook、透传和升级适配 | 原生处理重复维护成本确实升高后，再对白名单命令评估。不能默认全局改写或把项目方输出缩减比例当真实 Token |
| Context Mode | [上游说明](https://github.com/mksglu/context-mode)提供执行、文件处理、FTS 检索与会话存储，数据经过专用执行路径后可选择性返回 | 增加运行时、SQLite/索引、MCP、hook 和路由维护；普通调用仍打印原始结果时不会自动获得这一机制的效果。其文档也指出执行进程不是完整 OS 沙箱。[ELv2 许可](https://github.com/mksglu/context-mode#license)带来额外使用条款 | 反复查询同一大型输出、原生文件处理明显不便时再研究；本轮不引入这层许可证与运行依赖 |

RTK 需明确发行版：[当前许可说明](https://github.com/rtk-ai/rtk#license)区分 Apache-only `rtk-oss`、含 BUSL 组件的完整发行版和独立代理。无需新增订阅不等于所有发行版都没有额外许可条件。若未来评估，仅在符合约束的发行版上进行，并独立保留原始输出。

子 Agent 找到的一份 RTK 作者配对评估文件，主线重新访问未成功，因此其中数字没有纳入本报告。对无法复核的数字不作效果背书。

**方向 2：只复用仍有效的任务状态和验证。**

当前 Skill 已要求按需加载、复用已有证据、比例规划与验证；不能再写一遍同义规则，就声称增加了节省。值得验证的增量是一个小型任务记录是否真的跨越了实现、review、修正和恢复边界，并避免了实际重复工作。

记录只需包含：固定目标与验收项、已确认事实及原证据位置、事实与推断的区别、关键决定、已修改文件、未解决问题、已运行命令的范围/结果/artifact，以及每项证据和验证的有效状态。它不是每步都生成的正式计划，也不是把整段会话复制进文件后每轮重读。

复用前检查内容和条件：基线 revision 只是标识的一部分，还要考虑未提交/未追踪文件、相关依赖、配置、锁文件、生成文件、工具版本、命令参数、运行环境以及规则/验收的变化。源码事实与验证结果分开失效。不能只凭相同 HEAD、mtime 或“上次通过”复用。

- 源码事实所依赖的内容发生变化时，重新核验受影响结论；依赖闭包不确定时扩大失效范围。
- 验证覆盖的源码、配置、工具与环境仍相同且证据存在，才可能复用；检查缺失、超时或部分成功不能记成通过。
- 涉及外部服务、数据库状态、时间、随机性、并发或 flaky 行为时，源码哈希通常不足以证明验证仍有效。
- review 从现有证据与变更入口做必要复核，保留独立判断；不让 reviewer 从零重复整个探索，也不让它只接受上一个 Agent 的结论。
- 同一条工作线优先延续现有上下文；在实际恢复、必要交接或明显上下文压力时，使用宿主原生 compaction 和带指针的记录。不要给短任务人为制造换会话与压缩成本。

OpenAI [Compaction 文档](https://developers.openai.com/api/docs/guides/compaction)描述了压缩后携带状态的机制；官方返回的 opaque compaction 项需要按协议保留，不能把手写笔记当成可任意编辑它的许可。[Conversation state 文档](https://developers.openai.com/api/docs/guides/conversation-state)说明 `previous_response_id` 仍会计入链中的历史 input；仅减少传输 JSON 不等于减少模型 Token。[Prompt caching 文档](https://developers.openai.com/api/docs/guides/prompt-caching)说明缓存可复用前缀计算，不能据此从 total 中扣掉 cached input。

本方向可能产生丢失：摘要漏掉异常分支、原证据指针失效、规则过期或状态被错误合并。恢复方式是读取原 artifact、当前源文件和必要历史；若原件已删除，则不能声称摘要可逆。生成、更新、读取记录、压缩及恢复的模型与运行开销都要计入，尤其防止“节省后半程，漏算前半程”。

**增量验证的项目边界。**

| 项目能力 | 可以先做什么 | 不能据此替代什么 |
| --- | --- | --- |
| Maven reactor | 明确模块后，用原生模块选择缩短排错反馈；[官方文档](https://maven.apache.org/guides/mini/guide-multiple-modules.html)区分 dependencies 与 dependents | `-am` 只覆盖所选模块依赖，不自动证明所有下游消费者已验证；模块选择不能替代预先固定的最终 build/test 要求 |
| Vitest related/changed | 作为中间快速反馈；仍记录实际选择的测试 | [related 文档](https://vitest.dev/guide/cli#vitest-related)说明对运行期动态路径的限制；不能假设它覆盖所有行为和页面流程 |
| ESLint cache | 有明确安全范围时评估；优先只消除同状态的重复运行 | [官方文档](https://eslint.org/docs/latest/use/command-line-interface#caching)明确缓存不追踪跨文件依赖，类型/导入规则可复用陈旧结果；本轮不能宣称给当前配置加 cache 就保证等价 |
| TypeScript/Vue build state | 配置里存在 tsbuildinfo，说明有可进一步检查的构建状态机制 | 真实项目的前端规则明确要求改完执行 `npx vue-tsc -b --force` 与 `pnpm eslint`，涉及逻辑与页面流程还有相应测试；不能擅自删掉 `--force` 或缩小最终验收 |

缓存、daemon 与并行执行本身经常先改善墙钟时间；只有避免模型等待轮次、日志返回或重复决策，才可能减少真实 Token。不能用构建快了几秒来代替 usage 证据。当前没有证据支持为了本目标引入 Maven Build Cache、新 daemon、任务图平台或远端缓存。

**多 Agent 与阶段重复工作的处理。**

研究、实现或审查并行化，只应分配彼此独立且能交付明确证据的工作。给出已知事实、证据入口、未解决问题与所有权，避免多个 Agent 重新做同一轮环境与全仓探索。交接返回事实、位置、异常和未验证项；主线保留必要复核。

fresh context 有重新加载项目规则与 schema 的固定成本，full-history fork 又会复制历史；续用 Agent 可复用工作线，但会话会增长。选择依据应是聚合 usage 与任务依赖，不是默认“越多 Agent 越省”。[Claude 子 Agent 官方说明](https://code.claude.com/docs/en/sub-agents)可作为独立上下文、恢复和消耗的宿主实例；其他宿主仍需查其实际语义。

本轮不推荐默认多 Agent、每小步双重 review、多个规划框架或把原始日志交给另一个 LLM 摘要。它们可能有质量/并行价值，但把模型计算迁移到子 Agent 并不是 Token 减少。项目强制的 reviewer 和必要检查仍需保留并计入所有对照组。

**条件候选：工具 schema 按需发现。**

先审计模型实际可见的工具表示，而不是只数已安装 MCP 数量。完整定义仍在发给服务器的请求里，也可能没有进入模型初始上下文；网络 payload 大小不能充当 schema Token 实测。发现会增加往返，工具目录越小、实际使用比例越高，越可能不值得延迟加载。

| 宿主或协议层 | 已核实的机制 | 实验与推荐边界 |
| --- | --- | --- |
| OpenAI Responses API | [tool search](https://developers.openai.com/api/docs/guides/tools-tool-search)支持 deferred 工具；namespace/MCP 与单函数的初始可见信息不同，后者仍可能保留 name/description | API 支持不证明具体 Codex 客户端版本已经以同样方式接入。本会话可观察到 deferred namespaces 与原生程序编排，不应据旧报告全局目录混杂因素直接部署新网关 |
| Claude Code | [当前 MCP 文档](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search)说明默认按需发现，并列出模型、代理/平台、显式 always-load 等回退与覆盖条件 | 必须按实际版本、provider 和设置核验；不能沿用旧的“所有工具永远 upfront”或“固定阈值一定生效”结论 |
| OpenCode | [V2 文档](https://dev.opencode.ai/v2/docs/mcp-servers/)说明 Code Mode 默认启用；关闭后直接暴露工具 | 这是 V2 文档事实，不能推及 V1 或本机安装版本；主线未成功重新打开子 Agent 提供的 dev 设计源码，故不依赖该文件作进一步实现断言 |
| Gemini CLI | [当前 MCP 源码](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/mcp-client.ts)提供发现、注册与刷新；[PR #14375](https://github.com/google-gemini/gemini-cli/pull/14375)实现工具列表变更通知后的更新 | list_changed 支持不等于模型 schema 延迟加载。是否仍有可优化的 eager 成本，应查实际版本的模型请求与 usage |

当前不能推荐“只卸载或禁用工具来省 Token”作为保能力方案：那会改变能力集。按需发现需要让同一完整能力集仍可发现、可调用，并验证模糊查询、同名工具、分页、schema 更新与异常路径。

[MCP Slim](https://github.com/dopatools/mcp-slim)用 search/schema/call 三类入口替代工具目录，标注 MIT，首次语义搜索模型下载约 80 MB；这些是项目方机制与运行信息。更需要注意它还默认启用 schema/response compression，README 列出截断数组、字符串、去 metadata/null 等操作。若未来只测 schema deferral，应关闭这些额外变换，保留原始 schema、原始返回与直接恢复通道，否则同时改了多个机制，还可能删掉 URL、分页或语义相关字段。

在原生延迟加载可用时先使用原生能力。仅当目标宿主实测仍加载大量未用定义、原生能力不足、发现额外轮次有望被抵消时，才考虑代理。维护成本包括下游连接、鉴权、工具命名冲突、schema 更新、发现漏召回、依赖升级与新故障点。现在没有理由把 MCP Slim 加到当前工作流中。

**建议的小规模对照实验。**

本节是待执行协议，不是已测结果。准备阶段再冻结具体缺陷、任务全文、现有测试 ID、参考补丁/行为、报告和验收清单；本轮没有为选择任务而加载实现源码，也不假称已准备好可直接复跑的私有 fixture。

先做两个方向、每个方向一个有利案例加一个简单对照，每个 A/B 各一次，共 8 个完整任务运行。按预先固定的顺序交错 A→B、B→A。这个阶段只验证可行性、机制和风险，不作一般效率结论。若机制生效、两臂质量都达标且有利案例显示收益，再给有利案例各补两对；每项有利案例届时为 n=3。不要一开始重跑大型全组合矩阵。

| 单元 | 相同任务和项目状态 | A：当前正常工作流 | B：候选工作流 | 固定验收重点 |
| --- | --- | --- | --- | --- |
| O+ 输出处理有利例 | 在真实项目的独立副本中，选已有测试能捕获的生产缺陷，形成多段构建/测试诊断；完成定位、最小修复和原有最终验证。允许预录的真实报告用于稳定重放，但重放只能证明诊断/处理阶段，不能替代修复后真实验证 | 保持现有工具、reporter、截断与正常原生编排，不强制打印全日志或逐次手工调用 | 同样命令与验收；完整输出和报告落盘，本地确定性聚合后先返回必要状态/失败，再按需展开；使用已有执行器 | 所有根因、全部失败对象及范围、最小功能修复、未处理错误/收集失败/超时识别、原件可恢复、最终检查相同 |
| O− 简单对照 | 同项目一个已有测试覆盖的局部小缺陷，正常输出很少 | 正常直接完成 | 根据同一条件路由跳过不必要处理；若处理器仍介入，计入其开销 | 同一功能、边界和验证；不能靠少答或少测试过关 |
| S+ 状态复用有利例 | 一个真实两阶段任务：定位并实现后，在预先指定的自然恢复/交接边界继续处理一条相关反馈；两臂在同一时点收到相同的依赖/配置变化，验证旧状态失效 | 现有正常 resume/交接/自动 compaction 与比例验证，不人为要求重新探索 | 增加小型任务/证据/验证记录；在自然边界按需配合宿主 compaction；重用有效事实，检查并使受影响项失效；最终验证不减 | 原任务与反馈都完成；能发现旧结论失效；复用证据真实存在；最终验收完整 |
| S− 简单对照 | 一次即可完成的小改动，没有恢复或交接需求 | 正常直接完成 | 条件路由跳过记录/压缩仪式 | 相同质量；记录候选是否无谓增加轮次、文件或 Token |

若准备阶段发现正常工作流已经完成候选全部机制，则这是一项“已有覆盖”的发现，不得人为关闭基线优化再把差异归给候选。若 B 没有经过处理器、没读取记录、没有复用行为或没有实际压缩，则不能称为该机制生效。简单对照的正确跳过是路由行为验证，不是该机制使用后的节省证据。

O+ 是一套输出/本地处理工作流的整体比较，不能据其结果分别估计过滤、聚合和批处理各自的贡献。只有整体收益值得追查时才追加小型消融对照。

Schema 方向先做零模型的配置/源码检查和最小必要 trace 审计。只有仍有大量 eager schema 才单独增加两组小对照：大型目录只用少数工具，以及小目录/高使用比例的简单控制；同一宿主、同一模型、同一完整工具集，A 正常配置，B 只改变 discovery。原生开关优先，代理不在本轮安装范围内。不跨宿主或跨 provider 用不同模型做 Token 胜负比较。

**正式运行前冻结的条件。**

1. 模型、推理强度、宿主/版本、提示词、规则和 Skill 版本、同一能力集及报告策略。优先考虑此前已成功的 Desktop `gpt-6-luna / max`，但开始前仍需确认；本轮只观察到本机 CLI 为 0.144.4，旧报告的 CLI 失败不能假定已解决。模型不可用时先停止该比较，不能在某一臂静默 fallback。
2. 每个任务的相同源码状态：从当前授权状态制作独立副本，包含已授权的 dirty/untracked 内容和相关配置，记录内容哈希；不创建分支、提交或改动真实项目。只复制实验需要的文件，避免把私密配置或缓存塞进公开报告。
3. 使用现有测试，不新建应用单元测试。准备阶段可选择可重现的既有缺陷，或在实验副本中预置由已有测试捕获的生产代码缺陷；所需授权在开展实验时解决，本轮不实施。
4. 同一验收范围、异常情况、必要证据与输出要求。现有规则强制的类型检查、lint、测试、reviewer 或 e2e 不能为了省 Token删掉。e2e/浏览器等尚未获授权的操作，本轮不运行；未来选择无需它们的任务，或在正式实验前取得相同授权。
5. 初始依赖、构建产物、工具服务和 OS 缓存状态一致；分别记 cold/warm。不要 A 冷启动而 B 继承 A 的产物。模型缓存无法完全控制时，交错顺序并报告 cached/uncached，保留这一限制。
6. 工作者看不到其他运行、oracle、评分结果和 usage；固定同等时间/权限/恢复预算。停止、失败和重试都留记录，不仅保留成功样本。

**机制必须留下可核验事件。**

| 方向 | 必须出现的处理事件 | 同时要检查的反例 |
| --- | --- | --- |
| 输出/本地处理 | `command → 原始 artifact → 解析/聚合 → model-facing 结果`；对应 run ID、hash、范围、状态和展开记录 | 只装工具没走该路径；先把原文打印给模型；退出码被管道遮蔽；同一结果通过 text/structuredContent 重复返回；格式异常被当空结果 |
| 状态/验证复用 | 记录确实被后续阶段读取；至少一个有效事实/检查被复用，至少一个预置过期项被识别并重新核验 | 只写未读；只看 HEAD 忽略 dirty/config；为省 Token跳过最终必需验证；压缩项没有实际减少上下文；原件失效 |
| Schema 按需发现 | 初始请求未加载目标完整 schema，发现后加载并实际成功调用；能力集与原始 schema 可核对 | 工具只是可用没有调用；背后仍 eager加载；搜不到工具后直接省略任务；缓存折扣被当作 schema 不进入上下文 |

诊断用的字节数、字符数、原始行数和工具数量可以记录，但不能作为模型实测 Token；它们只用于说明机制是否经过该路径。若宿主不暴露完整请求，可用公开的 discovery/执行事件确认路径，同时明确无法验证的 schema 部分，不反推精确 schema Token。

**统一 usage 与成本记账。**

任务从接收任务开始，到完整交付和必要验证完成为止，包含探索、计划、实现、重试、review、修复、验证、压缩与交接的所有模型调用。所有主/子 Agent 和需要模型处理的 helper 都计入。

| 字段 | 定义与处理 |
| --- | --- |
| input | 规范化后的全部输入，包含缓存命中的输入 |
| cached input | input 中实际缓存读取的部分；不从 total 中扣除 |
| uncached input | input − cached input；缺少可比 cached 字段则留空；另保留 cache-write 的原始字段 |
| output | 宿主/服务端报告的完整 output；若 reasoning 为其子集，不再相加 |
| total | input + output；只在字段语义已确认且完整时计算 |
| 时间 | 任务墙钟时间、环境启动、命令耗时、模型等待与总体实验时长分别记录；并行墙钟不按各子任务简单相加 |
| 轮次 | 用户/任务 turn 与模型 response 分别记录；同时记录工具调用、展开、重试和空轮询数量 |
| 质量 | 逐项事实/功能/边界/异常/证据/验证通过情况，以及核心失败和未完成项 |

[Codex 非交互模式官方文档](https://learn.chatgpt.com/docs/non-interactive-mode)提供 `--json` 和 `turn.completed.usage`；这是可选记录入口，必须在实际版本上验证成功与字段范围。不能把同一 turn 的最终累计值和其中各 response 的 usage 再相加。若使用 Desktop，沿用能读取完整 host usage 的受支持入口，不因 CLI 更易解析就改变某一实验臂的宿主。

跨宿主统一字段不能机械照搬名字。例如 [Anthropic 官方 usage 说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#tracking-cache-performance)将 `input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens`分列；其总 input 需三者相加，cache read 是 cached input。OpenAI 常见 usage 的 cached 则是 input 的子集。各 provider 按文档规范化；不同 tokenizer 的绝对数不作跨模型效率排名。

采用以下一种计数基础，不能混用：

- 可取得逐请求记录时，以实际 provider/model response ID 去重求和，检查父 Agent 汇总是否已包含子 Agent；保留 self/inclusive 的 scope。工具事件与流式 usage 更新不当成新的请求。
- 只有累计记录时，每个 session/turn 只取完整最终累计值，或按已验证的单调区段求差；处理 reset/compaction 边界并与终值核对。不能累加重复快照。

usage 缺失、取消或失败时消耗不可见，保留失败记录与空字段，注明已知下界；不能记为 0 或用字符估算填补。若无法取得整项任务的真实 usage，该单元只能支持功能/机制检查，不能支持整个任务的 Token 节省结论。

最小逐运行记录建议包括：`run_id, task_id, arm, repeat, order, source_hash, model, effort, host_version, usage_scope, request_count, input, cached_input, uncached_input, cache_write_input, output, total, wall_seconds, model_responses, task_turns, tool_calls, retries, mechanism_active, quality_pass, failure_reason, raw_usage_ref, artifact_manifest_ref`。缺失数字保持空，不预填 0。

**把实验开销单列，但不隐藏方案自身的开销。**

| 账户 | 包含什么 | 不得移出的内容 |
| --- | --- | --- |
| 每个完整任务 | A/B 工作者与任务所需子 Agent、方案内脚本生成/修复、摘要、压缩、交接、失败恢复与最终验证 | 不能把 B 每次都需要的状态整理或“日志摘要 Agent”列成免费准备 |
| 一次性准备 | fixture 冻结、oracle、运行器/解析器开发与版本核验；并列报告新方案引入的额外准备 | 可复用模板的构建成本要报告摊销条件，不能声称它没有成本 |
| 调度 | 发起、等待、复制环境、收集记录、主线协调 | 如果 parent 同时参与实际解题，其解题部分归任务；无法拆分时保守披露 |
| 评估 | 匿名评分、独立完整验证、主线复核与统计报告 | A/B 工作者在交付前必须完成的检查仍属于各自任务，不由评估代做 |

报告任务账户和整个研究账户两套总量。本轮是调研而非 usage 实验，没有读取本轮主/子 Agent 的完整计量记录；不提供本轮研究的虚构总量。

**先判断能力，再看节省。**

评分表在正式运行前冻结，采用匿名输出与完整原始证据复核；等价表述和等价实现可通过，不以篇幅或精确字符串作为质量代理。必须同时满足请求范围、功能、边界与异常、必要证据、既定验证，并且无核心错误或未披露遗漏。对代码任务，检查最终 diff、现有测试和预先规定的契约/静态检查，不能只评最终解释。

若日志或缓存处理让答案漏掉一个必需失败、因旧状态作出错误决定或跳过必需验证，该次质量不通过，无论 Token 多低。保留该次所有消耗。不能删掉失败样本后只报剩余“平均节省”。

在完整质量通过的配对单元中报告每对差值、总量、median 与 min–max、耗时和轮次；有利/简单案例分别列示，不用有利场景平均数掩盖简单场景的负担。总 Token 降低、uncached 降低与耗时降低分别判断，不能互相替代。

小试的继续条件是：机制已实际生效、必要能力无观察到的下降、所有原证据可取回，且有利案例出现可重复检查的全任务收益。是否设置工程采纳阈值应在补跑前冻结；它不是统计显著性，也不是所有任务不退化的证明。样本小，只能得出覆盖案例内的描述性结论。

**目前不值得做的方向。**

- 再增加同类代码索引、为已可完成的检索任务重复排名；这不是本轮未解决的问题。
- 在已具备按需 discovery/程序编排的宿主上叠加同类 MCP 网关；先证明有未覆盖成本。
- 默认全局截断日志、只留尾部/首个错误、删 metadata/null/URL 或省略 Git 变更；没有完整恢复路径就不满足保能力目标。
- 为省 Token降低模型或推理强度、缩减任务/验收、强制短答案，或把消耗转给额外摘要/审查 Agent。
- 以 prompt-cache 折扣、server-side ID、工具后端缓存、RTK 类字符/字节估计或墙钟加速直接宣称 Token 减少。
- 对所有任务建立长期记忆库、每阶段重写计划、强制多轮审查/多 Agent，或频繁手动压缩；固定开销与失效风险先于收益出现。
- 未核验依赖与规则就用 affected-only、last-failed、lint cache 或去掉强制检查来代替最终验证。

后续先测原生输出/本地处理和状态复用两项；Schema 只在宿主审计出现实际缺口后补测。即使最后发现当前正常工作流已覆盖这些机制、没有净收益，这仍是有效结果，不需要为了增加工具而改变结论。
